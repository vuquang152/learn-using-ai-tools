# 05 — Tối ưu n8n

## Tách lượt chạy, số lần gọi API và tài nguyên

Một execution có thể gửi nhiều request nếu một node xử lý nhiều item hoặc thử lại. Ghi cả execution ID, item đầu vào, số request phía đích thực nhận và thời gian xử lý. Với gói tính theo execution, đối chiếu quy tắc đếm của gói. Với self-host, theo dõi thêm CPU, RAM và dung lượng lưu execution. [Gói và cách tính của n8n](https://n8n.io/pricing/)

## Tối ưu theo nguyên nhân

| Vấn đề | Thay đổi cần thử | Bằng chứng |
|---|---|---|
| Gọi model cho sự kiện đơn giản | Lọc payload sai và phân nhánh bằng điều kiện trước HTTP Request | Số request giảm, trạng thái giữ nguyên |
| Một sự kiện được giao nhiều lần | Dùng khóa ổn định và nơi lưu hỗ trợ kiểm tra trùng hoặc idempotency ở đích | Một tác động ghi cho cùng khóa |
| Đích trả 429 theo đợt | Đặt batch, khoảng chờ hoặc giới hạn song song phù hợp, tôn trọng hướng dẫn của đích | Ít 429 hơn và vẫn đạt thời gian mong đợi |
| Retry ăn hết thời gian | Đặt timeout, số lần thử tối đa và nhánh lỗi | Execution có điểm dừng và kết quả dự phòng |
| Payload lớn, khó xem lịch sử | Giữ metadata cần chẩn đoán, giới hạn dữ liệu lưu theo nhu cầu | Truy được run ID và lỗi với ít dữ liệu hơn |

[Xử lý rate limit](https://docs.n8n.io/integrations/builtin/rate-limits/) · [Workflow xử lý lỗi](https://docs.n8n.io/flow-logic/error-handling/)

## Bài đo nhanh

Dùng một lượt chạy thủ công nhận sáu item: hai thành công, hai build lỗi có khóa khác nhau, một bản sao của build lỗi và một payload sai. Đích HTTP là stub đếm request. So A gọi stub cho cả sáu item và B kiểm tra đầu vào, lọc build thành công, rồi loại bản sao trong batch trước khi gọi. Kỳ vọng 6 so với 2 request khi tắt retry, cùng hai bản nháp hợp lệ sau bước lọc đầu ra. Ghi số execution riêng. Để áp dụng cho sự kiện đến ở nhiều execution khác nhau, đối chiếu cách chống trùng bền vững đã học. [Xử lý lỗi và kiểm soát tác động](../03-n8n/02-reliable-workflows.md)
